# Requirements Document

## Introduction

DairySetu is a local B2B ordering network for dairy products that replaces chaotic WhatsApp-based order management between dairy distributors and shopkeepers. The platform enables shopkeepers to place orders quickly and accurately within a structured system, while giving distributors a clean, organized view of all orders, demand summaries, and billing — eliminating missed orders, calculation errors, and communication overload.

## Glossary

- **Distributor**: A dairy product distributor who manages products, pricing, order windows, and fulfills deliveries to connected shopkeepers.
- **Shopkeeper**: A retail shop owner who places orders for dairy products from their connected distributor.
- **Connection**: An approved relationship between a Shopkeeper and a Distributor that grants the Shopkeeper access to the Distributor's product catalog.
- **Connection_Code**: A unique alphanumeric code generated by the Distributor that a Shopkeeper can use to initiate a connection request.
- **Order**: A structured list of products and quantities submitted by a Shopkeeper to their connected Distributor.
- **Order_Window**: The time period defined by the Distributor during which normal orders are accepted (e.g., 6–8 PM).
- **Normal_Order**: An order placed before the Order_Window cutoff time.
- **Late_Order**: An order placed after the Order_Window cutoff time.
- **Order_Summary**: An aggregated view of all orders for a given delivery date, grouped by product and company.
- **Invoice**: A billing document generated for a Shopkeeper's order, containing itemized products, quantities, and totals.
- **WhatsApp_Bridge**: A subsystem that parses incoming WhatsApp messages and converts them into structured Orders.
- **Catalog**: The list of products and prices that a Distributor has configured and made available to connected Shopkeepers.
- **Delivery_Group**: A logical grouping of orders organized by area or route to assist the Distributor in planning deliveries.

## Requirements

### Requirement 1: Shopkeeper–Distributor Connection

**User Story:** As a shopkeeper, I want to connect with my distributor using a phone number or unique code, so that I can access their product catalog and place orders.

#### Acceptance Criteria

1. WHEN a Shopkeeper submits a connection request using a valid Distributor phone number or Connection_Code, THE System SHALL create a pending Connection and notify the Distributor.
2. WHEN a Distributor approves a pending Connection, THE System SHALL activate the Connection and notify the Shopkeeper.
3. WHEN a Distributor rejects a pending Connection, THE System SHALL remove the pending Connection and notify the Shopkeeper.
4. WHILE a Connection is pending, THE System SHALL prevent the Shopkeeper from accessing the Distributor's Catalog or placing Orders.
5. WHILE a Connection is active, THE System SHALL restrict the Shopkeeper's Catalog view to only the products of their connected Distributor.
6. IF a Shopkeeper submits a connection request with a phone number or Connection_Code that does not match any registered Distributor, THEN THE System SHALL return a descriptive error message to the Shopkeeper.
7. THE System SHALL allow each Shopkeeper to maintain at most one active Connection at a time.

---

### Requirement 2: Product Catalog Management

**User Story:** As a distributor, I want to manage my product catalog with multiple products and brands, so that shopkeepers always see accurate and up-to-date offerings.

#### Acceptance Criteria

1. THE Distributor SHALL be able to add, edit, and remove products in the Catalog, specifying product name, brand (e.g., Amul, Saras, local), category (e.g., milk, paneer, curd, butter, ghee), unit, and price.
2. WHEN a Distributor updates a product's price or availability, THE System SHALL reflect the change in the Catalog immediately for all connected Shopkeepers.
3. WHILE a product is marked as unavailable by the Distributor, THE System SHALL hide that product from the Shopkeeper's ordering view.
4. THE System SHALL support a minimum of 50 products per Distributor Catalog.

---

### Requirement 3: Order Placement by Shopkeeper

**User Story:** As a shopkeeper, I want to quickly browse products and place an order in seconds, so that I can complete my daily ordering without effort or confusion.

#### Acceptance Criteria

1. WHILE a Connection is active, THE System SHALL display the Shopkeeper's Catalog with product name, brand, unit, and price.
2. THE System SHALL allow a Shopkeeper to select a product quantity using a numeric input or increment/decrement control.
3. WHEN a Shopkeeper submits an Order, THE System SHALL record the Order with a timestamp, the Shopkeeper's identity, and the list of products and quantities.
4. WHEN a Shopkeeper submits an Order before the Order_Window cutoff, THE System SHALL classify the Order as a Normal_Order.
5. WHEN a Shopkeeper submits an Order after the Order_Window cutoff, THE System SHALL classify the Order as a Late_Order and display a clear notice to the Shopkeeper that the order is late and subject to Distributor approval.
6. IF a Shopkeeper attempts to place an Order with zero items selected, THEN THE System SHALL prevent submission and display a validation message.
7. THE System SHALL allow a Shopkeeper to review the Order summary before final submission.

---

### Requirement 4: Order Window Configuration

**User Story:** As a distributor, I want to configure the daily order cutoff time, so that I can manage my workflow and plan deliveries effectively.

#### Acceptance Criteria

1. THE Distributor SHALL be able to set a daily Order_Window start time and cutoff time.
2. WHEN the Order_Window cutoff time passes, THE System SHALL automatically begin classifying new incoming Orders as Late_Orders.
3. THE System SHALL display the current Order_Window cutoff time to Shopkeepers on the ordering screen.

---

### Requirement 5: Distributor Order Dashboard

**User Story:** As a distributor, I want a clean overview of all orders separated by type, so that I can manage my day without confusion or mental overload.

#### Acceptance Criteria

1. THE System SHALL display all Normal_Orders and Late_Orders in separate, clearly labeled sections on the Distributor's dashboard.
2. WHEN a Late_Order is received, THE System SHALL present the Distributor with an explicit accept or reject action for that order.
3. WHEN a Distributor accepts a Late_Order, THE System SHALL include it in the Order_Summary alongside Normal_Orders.
4. WHEN a Distributor rejects a Late_Order, THE System SHALL notify the Shopkeeper that their late order was not accepted.
5. THE System SHALL display the total count of pending Normal_Orders and pending Late_Orders as separate figures on the dashboard.
6. THE System SHALL allow the Distributor to view individual Order details including Shopkeeper name, products, quantities, and order timestamp.

---

### Requirement 6: Order Summary and Demand Aggregation

**User Story:** As a distributor, I want the system to automatically combine all orders into a total demand view, so that I can plan procurement and delivery without manual calculation.

#### Acceptance Criteria

1. THE System SHALL generate an Order_Summary for each delivery date that aggregates total quantity required per product across all accepted Normal_Orders and accepted Late_Orders.
2. THE Order_Summary SHALL group products by brand and category.
3. WHEN a new Order is accepted or a Late_Order is approved, THE System SHALL update the Order_Summary in real time.
4. THE System SHALL display the Order_Summary to the Distributor in a tabular format showing product name, brand, unit, and total quantity.

---

### Requirement 7: Delivery Grouping

**User Story:** As a distributor, I want orders grouped by delivery area or route, so that I can plan and execute deliveries efficiently.

#### Acceptance Criteria

1. THE System SHALL allow the Distributor to assign each Shopkeeper to a named Delivery_Group (e.g., area or route name).
2. THE System SHALL display orders on the Distributor dashboard organized by Delivery_Group.
3. THE System SHALL show the total product quantities required per Delivery_Group in the Order_Summary.

---

### Requirement 8: Billing and Invoice Generation

**User Story:** As a distributor, I want to generate and share invoices easily, so that billing is accurate and requires minimal manual effort.

#### Acceptance Criteria

1. THE System SHALL generate an Invoice for each accepted Order, containing Shopkeeper name, order date, itemized product list with quantities and unit prices, and total amount.
2. THE Distributor SHALL be able to export an Invoice as a PDF file.
3. THE Distributor SHALL be able to share an Invoice directly via WhatsApp or other available sharing mechanisms on the device.
4. IF an Order is modified after Invoice generation, THEN THE System SHALL mark the existing Invoice as outdated and allow the Distributor to regenerate it.

---

### Requirement 9: WhatsApp Bridge

**User Story:** As a shopkeeper, I want to place orders by sending a WhatsApp message in my usual way, so that I can continue my existing habit while the system organizes my order automatically.

#### Acceptance Criteria

1. WHEN a Shopkeeper sends a WhatsApp message to the Distributor's registered WhatsApp Bridge number, THE System SHALL parse the message and attempt to extract product names and quantities.
2. WHEN the WhatsApp_Bridge successfully parses a message into a valid Order, THE System SHALL create the Order on behalf of the Shopkeeper and apply the same Normal_Order or Late_Order classification rules based on the message timestamp.
3. WHEN the WhatsApp_Bridge cannot parse a message into a valid Order, THE System SHALL send an automated reply to the Shopkeeper indicating the message was not understood and providing a simple format example.
4. THE WhatsApp_Bridge SHALL confirm each successfully parsed Order by sending a structured summary reply to the Shopkeeper via WhatsApp.
5. THE System SHALL associate incoming WhatsApp messages with a registered Shopkeeper based on the sender's phone number.
6. IF a WhatsApp message is received from a phone number not associated with any registered Shopkeeper, THEN THE System SHALL send an automated reply with instructions to register on the platform.

---

### Requirement 10: Notifications

**User Story:** As a distributor and shopkeeper, I want to receive relevant, grouped notifications, so that I stay informed without being overwhelmed.

#### Acceptance Criteria

1. WHEN a Shopkeeper places a Normal_Order, THE System SHALL send a single confirmation notification to the Shopkeeper.
2. WHEN a Late_Order is received, THE System SHALL notify the Distributor once per Late_Order, not once per product line.
3. THE System SHALL group multiple order notifications received within a 5-minute window into a single batched notification for the Distributor.
4. WHEN a Distributor accepts or rejects a Late_Order, THE System SHALL send a single status notification to the affected Shopkeeper.
5. THE System SHALL NOT send notifications to a user for events that do not require their action or awareness.

---

### Requirement 11: Authentication and User Accounts

**User Story:** As a user, I want to securely log in to my account, so that my orders and data are protected.

#### Acceptance Criteria

1. THE System SHALL require each user to authenticate using a verified phone number via OTP before accessing any feature.
2. WHEN a user registers, THE System SHALL require them to select a role: Distributor or Shopkeeper.
3. THE System SHALL maintain separate role-based views and permissions for Distributors and Shopkeepers.
4. IF an unauthenticated user attempts to access any protected resource, THEN THE System SHALL redirect the user to the login screen.
